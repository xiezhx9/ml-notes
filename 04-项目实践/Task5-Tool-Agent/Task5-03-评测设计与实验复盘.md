# Task 5.3：评测设计与实验复盘

> [!summary] 必须掌握
> 先定义要验证的能力，再设计任务、指标与对照。Agent 的答案、动作、证据使用和成本应分别观察；实验最有价值的产物，是能解释失败并指导下一次修改的证据。

返回总览：[[Task5-Tool-Agent学习索引]]

## 1. 先明确“通过”是什么意思

| 验收层次 | 本项目怎样做 | 主要盲点 |
|---|---|---|
| 工具可用性 M1 | 四工具各测一组输入 | 冒烟通过不代表边界输入、安全和网络均可靠 |
| 循环与回灌 M2/M3 | 检查动作路由、错误反馈、终止；可用假模型隔离验证 | 当前缺少独立且完整的分支测试 |
| 答案质量 M4 | 最终答案关键词命中率 >60% | 可凭记忆答对，没有证明使用工具 |
| 工具流程 S1–S3 | 答案正确且覆盖期望工具 | 工具名出现不代表参数正确或证据被使用 |
| 错误恢复 S4 | 已注入、有补救、答案正确；总体恢复率 >40% | 补救动作只是宽松的行为代理指标 |

十道题下，M4 至少 7 题通过，恢复验收至少 5 题通过。S1–S3 没有统一硬编码及格线，重点是对照是否有效。

任务与 gold（参考答案及验收条件）必须一致。例如数据集中“计算平方根并格式化”的第 8 题，若只问数学结果，一个工具就能合理完成；若要研究双工具串联，就要在题目中明确这项要求。这里的“第 8 题”指 Task5 测试数据，和课程 Task 编号无关。

## 2. 四个核心指标：答案、覆盖、精确选择、联合成功

对第 $i$ 次运行，设：

- $A_i$：最终答案是否命中当前标准；
- $E_i$：期望工具集合；$U_i$：轨迹中记录的工具名集合；
- $C_i$：是否覆盖要求的全部工具；
- $X_i$：工具集合是否恰好相同；
- $J_i$：答案和覆盖是否同时通过。

$$
C_i=\mathbf{1}[E_i\subseteq U_i],\qquad
X_i=\mathbf{1}[E_i=U_i],\qquad
J_i=A_i\land C_i.
$$

任一项的总体比例，都用该项通过次数除以全部运行次数 $N$。

例如要求 wiki 与 calculator：只用 wiki 答对时，$A=1,C=0,J=0$；两个都用且答对时，$J=1$；再多用 sandbox，$J$ 仍为 1，但 $X=0$。重复 calculator 不改变工具集合，却会增加调用成本。

当前覆盖统计只看动作名，不验证执行成功、调用顺序或参数依赖。因此还应抽查：**calculator 的年份是否来自此前 wiki 的真实返回？**

### 关键词评分器也需要验收

当前匹配先统一大小写、去逗号和空白，再做子串匹配。例如：

```json
["1947", ["78", "79"]]
```

顶层是 AND，子列表是 OR：最终答案需要出生年份和年龄。S2 中出现过已查到年份、也算对年龄，却只回答年龄的样本，这属于最终回答遗漏。

同时，关键词规则可能：

- 把“位数为 6”误判为不符合“6位”：假阴性；
- 让期望 `2` 匹配到 `12`：假阳性；
- 接受数值等价但格式不符的答案：没有测到原本的格式要求。

改进时，数值题用容差，字段题用结构化字段检查，代码题运行测试，证据题核对来源；需要语义 judge 时，也要用人工样本校准。不能只增加关键词直到分数变好。

## 3. 错误恢复为什么需要两个分母

S4 在每题第一次工具**正常返回后**，把可见结果替换成一次“无可用结果”的错误提示。模型接收 Observation 后继续选择动作。工具本身先抛异常，则不会触发这个注入位置。

设 $I_i$ 为记录到注入，$R_i$ 为注入后有补救动作，恢复成功定义为：

$$
K_i=I_i\land R_i\land A_i.
$$

当前 `retried` 的实际含义是：注入后又有工具正常返回，换工具也算；返回值是否真正有用并未被严格检查。它更接近“补救尝试”，不等于必然修复。

历史报告共 30 次运行，记录到注入 22 次，补救 21 次，恢复 20 次：

$$
\text{总体恢复率}=\frac{20}{30}=66.67\%,\qquad
\text{注入条件下恢复率}=\frac{20}{22}=90.91\%.
$$

前者反映整批任务的结果，后者反映记录到故障机会后有多少恢复。只报后者会掩盖未触发注入的任务；还应一起看注入率 $22/30$。

两个 API 异常样本缺少完整中间轨迹，报告将注入记为 False，所以 22 是“可见记录数”。这一问题说明：**未知状态不应直接当作未发生，异常时也要保存部分 Trace。**

S4 的成功条件未额外要求工具覆盖；不能把它与 S1–S3 的联合成功混用。同批次没有无注入对照，也就不能直接计算故障造成的净损失。

## 4. S1–S4 留下的四条主要经验

以下取自 2026-09-09～10 保存的报告。每个变体均为十题三轮、30 次运行；S1/S3/S4 使用 DeepSeek，S2 比较三个远程 Qwen 规模。

| 实验 | 想研究什么 | 保存结果 |
|---|---|---|
| [S1 框架对照](https://github.com/xiezhx9/react-tool-agent-from-scratch/blob/f757319006abedf4e1c4ae8a30b7dc639aba48e6/eval/results/s1_qwen_agent/comparison.json) | 同模型、同工具，改编排与调用协议 | 手写联合成功 27/30；Qwen-Agent 30/30 |
| [S2 模型对照](https://github.com/xiezhx9/react-tool-agent-from-scratch/blob/f757319006abedf4e1c4ae8a30b7dc639aba48e6/eval/results/s2_model_sizes/comparison.json) | 固定 Agent 和 prompt，改模型 | 0.6B：11/30；8B：19/30；14B：23/30 |
| [S3 Prompt 消融](https://github.com/xiezhx9/react-tool-agent-from-scratch/blob/f757319006abedf4e1c4ae8a30b7dc639aba48e6/eval/results/s3_prompts/comparison.json) | 移除示例，或精简工具说明 | baseline：25/30；去示例：25/30；简化说明：20/30 |
| [S4 错误反馈](https://github.com/xiezhx9/react-tool-agent-from-scratch/blob/f757319006abedf4e1c4ae8a30b7dc639aba48e6/eval/results/s4_error_recovery/s4_result.json) | 注入失败后能否继续完成 | 总体恢复 20/30；注入条件下 20/22 |

**S1：编排方式会影响同一模型的表现。** 框架组仍使用 DeepSeek，Assistant 接管循环并调用相同底层工具。它的工具流程更完整，但调用更多、耗时更高。实验同时改变了协议、prompt 和循环，不能把收益全归因于框架内置 prompt。下一步可加入“手写原生 tool calls”组，尽量统一策略与预算，再分别比较协议和框架。

**S2：衡量整条任务的效率。** 14B 每题约 6.31 秒，8B 约 7.90 秒；8B 更多次反复调用甚至耗尽预算。更大的模型可能通过减少无效尝试缩短总耗时，但远程服务资源也是混杂因素。没有完整 usage 和价格数据，不能只凭速度判断性价比。

**S3：消融实验允许没有收益。** baseline 实际只有一个简单示例，去掉后本次联合成功未变；这不说明所有 few-shot 都无效。简化说明少成功 5 次，即下降 16.67 个百分点，步骤减少还可能来自跳过必要工具。后续应测试匹配目标行为的多步/恢复示例，并用独立题目确认泛化。

**S4：观察错误后的策略变化。** 换工具、改参数、同参数重试和停止应分开统计。下一轮可对同一任务做正常/故障配对，固定故障位置与外部返回，比较成功损失、额外动作和恢复策略，而不只记录“又调用了一次”。

> [!note] 结果的适用范围
> S1 与早期 S2/S3 的关键词规则存在差异，部分题目也曾改写；历史报告未完整保存输入原文。上表用于回顾各实验内部结果，不用于跨批次排名。本次整理没有重跑实验。

## 5. 从这个项目迁移出去的评测方法

1. **先定义失败。** 区分格式错、选错工具、参数错、执行失败、忽视证据、提前收尾与评分误判，再选相应指标。
2. **固定可控条件。** 保留任务与 gold、prompt、代码版本、模型配置和预算；尽量使用确定性工具夹具。比较框架时，相同 max_steps 名称不保证限制的是同一种动作。
3. **隔离程序和模型。** 假模型固定输出可检验解析、真实工具执行与回灌；真实模型实验检验决策。前者通过不能作为后者成绩。
4. **成对看改善与退步。** 十题重复三轮有助于观察波动，但仍只有十种任务。优化 prompt 用开发集，最终结论用未参与调试的题；别在同一小题集上反复调到高分。
5. **先合计数，再算比例。** 两轮 9/10 和 1/2，合并为 10/12，而不是无权平均成 70%。统计推断需考虑同题重复的相关性，固定温度与执行顺序也不保证远程服务完全确定。

要验证模型是否利用 Observation，可固定任务结构，改变工具返回的关键事实并同步更新 gold，观察下一步参数和答案是否随之正确变化。只看工具名出现过，无法完成这个检验。

## 6. 实际验收与报告阅读顺序

按 `工具冒烟 → 固定输出的循环检查 → 真实任务自检 → 对照实验 → 失败样本复盘` 执行。假模型检查至少覆盖正常结束、解析错误、工具失败、反馈回灌和预算耗尽。

需要复现时：

```bash
cd /path/to/task-5-tool-agent
uv sync --locked --extra qwen-agent
uv run python eval/run.py
uv run --extra qwen-agent python run_experiments.py s1 --repetitions 3
uv run python run_experiments.py s2 --repetitions 3
uv run python run_experiments.py s3 --repetitions 3
uv run python run_experiments.py s4 --repetitions 3
```

这些命令会调用远程服务并覆盖固定输出，重跑前保留旧报告；S2 使用单独的 endpoint/model/key 配置。自检在 `eval/result.json`，实验在 `eval/results/`。

读报告按 `配置与题集 → 每组分母 → 指标 → 逐题 Trace → 结论`。当前自检壳会捕获失败并写入 JSON，退出码 0 不保证通过；wiki 的网络跳过也应与通过区分。保存的历史自检为 M1 通过、M4 10/10、恢复 10/10，属于另一批运行。

看成本时要结合成功率、总时延、请求数与 token；prompt 字符数和 steps 都不能直接代表计费。失败请求和中间重试也有成本，应计入统计。

## 7. 自测

1. 答案正确但未调用要求的工具，M4 与联合成功分别怎么判？工具全部出现又能证明什么？
	1. M4成功，联合不成功；覆盖完全，但是不能说吗结果正确
2. 怎样用一个例子说明关键词评分器的假阳性与假阴性？如何改进？
	1. “12”含“2”可能被误过；“位数为 6”可能不匹配“6位”而误判失败。应按任务使用数值容差、字段校验、执行测试或证据核对，并人工抽查。
3. 30 次运行、22 次记录到注入、20 次恢复，两个恢复率分别回答什么问题？
	1. 20/30=66.67% 是整批运行的恢复率；20/22≈90.91% 是记录到注入之后的恢复率。还需报告注入率及未知状态，避免只选择有机会恢复的样本。
4. 同一个模型在框架组更好，为什么不能直接认定“内置 prompt 更强”？怎样增加对照？
	1. 编排、协议和 prompt 都变了。增加手写原生调用组，统一模型、工具、策略和预算，才能逐步区分来源。
5. 去掉一个示例没有退步，能否证明 few-shot 无用？精简 prompt 后更快就一定更好吗？
	1. 只能说这组模型、题目和示例下未见净增益；更快可能来自遗漏步骤。应在任务质量达到要求后比较总成本，并在新题上验证。
6. 十题重复三轮是不是三十道独立题？9/10 与 1/2 应怎样聚合？
	1. 重复运行用于观察波动；聚合应先加成功数和样本数，得到 10/12≈83.33%。若做显著性分析，应考虑同题结果的相关性。
7. 怎样区分循环实现错误与模型决策错误？怎样进一步验证模型真的使用了观察？
	1. 用假模型验证解析、执行、回灌和终止；用真实模型测决策。再受控改变 Observation 中的事实并同步 gold，检查后续动作和答案是否正确跟随。
8. “测试命令成功退出”与“验收通过”有什么区别？修改题目和修改评分器需要怎样处理历史结果？
	1. 必须读取 pass、指标及失败细节。修改匹配规则可另存离线重评分；改题会改变模型输入，需要重跑，并保留原报告与版本。
