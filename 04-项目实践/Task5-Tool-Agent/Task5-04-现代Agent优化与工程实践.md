# Task 5.4：现代 Agent 优化与工程实践

> [!summary] 必须掌握
> 优化要回答三个问题：失败发生在哪一层，新增机制改变了什么，用什么指标确认收益。现代 Agent 的很多工程能力，都是在基础反馈循环上改善上下文、执行、状态与验证。

返回总览：[[Task5-Tool-Agent学习索引]]

本篇是从 Task5 提炼的工程方法与后续设计；下列扩展不代表项目均已实现。

## 1. 先从失败找改动位置

| 观察到的问题 | 优先考虑的改进 | 验证指标 |
|---|---|---|
| Action 格式经常错 | 原生调用协议、Schema 校验 | 格式/参数有效率 |
| 工具选错或漏步骤 | 明确工具职责、子问题清单和完成条件 | 工具覆盖、遗漏率、联合成功 |
| 工具结果为空或不相关 | 明确返回状态、来源和错误类型 | 有效结果率、正确补救率 |
| 相同失败不断重复 | 有限重试、进度检查、分类处理错误 | 无进展动作数、恢复率、停止原因 |
| 历史越来越长 | 按需读取、压缩、结构化工作记忆 | 输入 token、证据保留、长任务成功率 |
| 独立查询耗时累加 | 并行执行 | 总时延、冲突与错配率 |
| 中断后丢进度或重复操作 | 持久化状态、调用 ID、幂等 | 恢复成功、重复副作用 |
| “已完成”却漏要求 | 独立完成检查、可执行验收 | 提前收尾率、真实任务通过率 |

一次优先解决一类主要失败，然后回到 [[Task5-03-评测设计与实验复盘]] 做对照。清晰工具接口和按需增加复杂度，也是 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 中值得长期保留的设计原则。

## 2. 规划和反思要落到可观察状态

已知且稳定的步骤适合写成 workflow；路径取决于检索或执行结果时，让模型动态选择更合适。任务较长时，显式维护：

`目标 / 已完成 / 待完成 / 证据引用 / 最近错误 / 剩余预算`

这样能提醒模型“已拿到出生年份，还差计算与完整回答”，比每轮重新读全部历史更容易检查进度。计划需要随着观察更新，不能把一开始列出的步骤当作事实。

反思应体现为策略调整：

| 错误 | 合理的后续动作 |
|---|---|
| 缺少参数 | 补参数后再调用 |
| 搜索未命中 | 改查询、换已授权来源 |
| 临时超时 | 在预算内有限重试 |
| 永久权限拒绝 | 停止该路径，说明缺少的能力 |
| 相同动作持续无进展 | 换策略或给出明确未完成原因 |

相同参数重试一次不一定错误。应结合错误类别、次数和新信息判断；增加一段“我反思了”的文字，不能替代行为改善。

## 3. 上下文、缓存与记忆分别解决什么

| 方法 | 作用 | 需要关注 |
|---|---|---|
| 按需读取 | 先看目录/摘要，需要时再读正文 | 是否漏掉关键证据 |
| Compaction | 用摘要与状态替代部分历史 | 保留用户约束、未解决问题、证据出处，避免摘要失真 |
| 工作记忆 | 保存已完成事项、尝试与证据索引 | 下一轮要主动读回；陈旧记忆需要更新 |
| Prompt cache | 复用相同前缀的计算 | 支持与计费依后端；不等于缩短模型可见内容 |
| 工具结果缓存 | 复用已查结果 | 来源、时效与失效策略 |

外部文件中的记录只有读入上下文后，才能影响这一轮决策。工作记忆主要保存状态，RAG 主要按需找知识，两者可以配合。

例如查很多文件时，先保留“路径、相关片段、行号”，需要时再补读，比把所有全文持续塞进历史更容易控制成本。这里的目标是留下足够且相关的信息；[Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 讨论了按需获取、压缩和结构化笔记等方法。

## 4. 并行与 Subagent：先检查依赖

两个互不依赖的检索可以并行；“先查出生年份，再把年份传给计算器”有数据依赖，必须先取得真实输入。

Subagent 可以承接范围明确、相对独立的子任务，用独立上下文探索后返回结论与证据。主 Agent 仍要检查结果、处理冲突并汇总；委派本身不会保证正确。

衡量成本时应汇总所有实际模型请求：

$$
\mathrm{TotalTokens}
=\sum_{q\in\text{所有模型请求}}
(\mathrm{InputTokens}_q+\mathrm{OutputTokens}_q).
$$

包括主 Agent、子 Agent、额外协调与重试。相同文本在不同请求中重复输入仍分别计入；同一请求被多份日志记录则只能统计一次。主 Agent 上下文更短，并不自动说明总 token 或费用更低。

## 5. 让执行可恢复、完成可验证

**保留运行证据。** 每步记录任务 ID、调用 ID、工具名、参数、执行状态、结果/来源、耗时与模型 usage。异常时保存 partial trace；不确定是否执行过的动作应标 unknown，避免把缺失记录当作 False。

**区分持久化与幂等。** Checkpoint 让程序记住恢复位置；幂等让重复操作不产生额外副作用。例如请求已经成功发送但回包丢失，恢复后直接重试可能发送两次，需要幂等键或外部状态核验。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) 展示了状态检查点与恢复机制。

**用完成条件收尾。** 明确区分 completed、预算耗尽、模型请求失败、工具不可用和需要用户输入。对于 Coding Agent，最后一次修改后重新运行相关测试；修改前的通过结果不能证明当前版本正确。普通问候无需工具，不应把 Task5 特定题集的必用工具条件套到所有场景。

## 6. 怎样判断优化值得保留

在相同题集和可比预算下，同时报告任务成功率、总耗时和完整成本；必要时看较慢任务的 P95，避免均值隐藏长尾。统计失败和重试开销。

项目没有完整价格与 usage 数据时，应承认成本结论暂不充分。后续可用：

$$
\text{每次成功的平均成本}
=\frac{\text{整批运行总成本（含失败）}}{\text{成功次数}}.
$$

这个指标必须与成功率一起看，不能只统计成功样本的费用；没有成功时也不能报告有限的“每次成功成本”。

例如 S2 中较大的模型用了更少动作，说明端到端优化不只取决于单次模型速度。可以进一步测“简单任务用小模型、明确失败后升级模型”，但要把升级和重复探索也计入总成本。

## 7. 自测

1. 什么情况下固定 workflow 更合适？什么情况下值得让模型动态规划？
	1. 固定、稳定、可验证的步骤适合 workflow；需要依据环境反馈决定查询、修改或恢复路径时，动态决策更有价值。复杂任务再增加可更新的进度状态。
2. 怎样判断“反思”产生了价值，而不是只增加文字和请求？
	1. 检查是否修正参数、换有效路径、减少无进展重试，并提高成功或降低成本。额外反思调用也必须进入成本统计。
3. Prompt cache、compaction、工作记忆有什么区别？
	1. 一个长时间运行的 Agent 可能这样工作：
		1. 工作记忆保存当前目标、已完成步骤和下一步。
		2. 每次模型调用重复使用系统提示和工具定义，Prompt cache 降低开销。
		3. 对话接近上下文上限时，compaction 把旧历史压缩。
		4. 压缩后，Agent 根据保留下来的工作记忆继续执行。
		5. 任务结束后，少量稳定知识可能进入长期记忆。
	2. 最关键的区别是：
		- **Prompt cache 解决“重复计算”。**
		- **Compaction 解决“上下文放不下”。**
		- **工作记忆解决“Agent 接下来需要记住什么”。**
4. 怎样判断两个动作可以并行？Subagent 让主上下文变短能否证明更省钱？
	1. 后一步依赖前一步结果时不能直接并行；Subagent 需要汇总全部分支、协调和重试成本，不能只看主 Agent。
5. Checkpoint 为什么不能自动避免重复副作用？partial trace 为什么重要？
	1. Checkpoint 只能记录“Agent 当时认为自己进行到哪里”，Agent 框架通常不知道：
		- 一次工具调用是否已经在服务端生效
		- 超时代表执行失败，还是执行成功但响应丢失
		- 这个操作是否幂等
		- 两次参数相同的调用是重试，还是用户真的想执行两次
		- 副作用能否撤销
		- 应该重试、查询、补偿还是请求人工确认
	2. 提供可回溯的指标
6. 一次优化让平均耗时下降，但成功率也下降，该怎样评价？Coding Agent 的完成证据是什么？
	1. 先检查是否因漏步骤而更快，再在明确的质量要求下比较整批成本与时延。Coding Agent 的证据包括当前代码上的相关测试结果，以及任务要求确实被满足。

### 自测标准答案

> [!success]- 标准答案：1. 看路径是否预先确定
> 固定、稳定、可验证的步骤适合 workflow；需要依据环境反馈决定查询、修改或恢复路径时，动态决策更有价值。复杂任务再增加可更新的进度状态。

> [!success]- 标准答案：2. 看后续行为与任务结果
> 检查是否修正参数、换有效路径、减少无进展重试，并提高成功或降低成本。额外反思调用也必须进入成本统计。

> [!success]- 标准答案：3. 计算复用、内容重组、状态保存
> Cache 复用前缀计算；compaction 改变下一轮可见历史；工作记忆保存进度与证据，需要读回。后两者都可能引入遗漏或陈旧信息。

> [!success]- 标准答案：4. 无数据依赖且无共享状态冲突
> 后一步依赖前一步结果时不能直接并行；独立检索更适合。Subagent 需要汇总全部分支、协调和重试成本，不能只看主 Agent。

> [!success]- 标准答案：5. 程序状态与外部状态可能不一致
> 动作可能已生效而结果未保存，恢复后会重复执行。幂等键或状态核验处理副作用，partial trace 帮助判断失败位置与未知状态。

> [!success]- 标准答案：6. 质量与成本一起比较
> 先检查是否因漏步骤而更快，再在明确的质量要求下比较整批成本与时延。Coding Agent 的证据包括当前代码上的相关测试结果，以及任务要求确实被满足。
