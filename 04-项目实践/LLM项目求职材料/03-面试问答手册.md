# LLM / RAG / Agent 项目面试问答手册

> [!summary]
> 回答项目题时使用“**背景—约束—决策—证据—边界—下一步**”六步法。先讲为什么做和解决什么问题，再讲设计与数据，最后主动交代局限。能解释失败实验，通常比只展示一个漂亮数字更可信。

## 1. 自我介绍模板

### 60 秒版本

> 我主要沿着大模型应用与 Agent 工程方向学习和实践。底层部分，我手写过 Transformer、BPE、RoPE、KV Cache，以及基于 Qwen2.5 的 LoRA、SFT 和 DPO；应用部分，我从零搭建了中文 RAG，并使用 Recall、MRR 和 RAGAS 分层评测；最近重点完成了工具调用与 Coding Agent，从文本 ReAct、原生 Function Calling 扩展到 MCP、Skill、Subagent 和 SWE-bench 官方验收。我的特点是不会只停留在 Demo，而会补齐错误恢复、路径安全、Trace、对照实验和失败分析。例如 Coding Agent 当前有 85 项离线测试，在 3 个固定 SWE-bench Lite 实例上正式通过 1 个。我希望继续做 LLM 应用、RAG 或 Agent 方向的工程工作。

### 30 秒版本

> 我的方向是 LLM 应用和 Agent 工程，完整做过模型原理与微调、中文 RAG、ReAct 和 MCP Coding Agent。项目中比较重视评测闭环与安全执行，不只看最终答案，还拆分工具选择、错误恢复、Token、延迟和官方测试。当前主项目有 85 项离线测试，并完成了 SWE-bench Docker 验收。

## 2. 三个项目的三分钟讲法

### 2.1 Coding Agent

> 我想验证一个代码 Agent 除了能调用模型，还需要哪些运行时能力。因此先实现手写 ReAct，理解 Thought、Action、Observation 的循环；随后改用模型原生工具调用，通过 MCP stdio 暴露仓库检索、读写、Patch、测试和 Git Diff 等能力。
>
> 工程上重点解决了三类问题。第一是安全边界：所有路径都解析到工作区根目录下，防止绝对路径、`..` 和符号链接越界，同时保护 `.git` 和测试文件。第二是状态一致性：写入代码后旧测试结果必须失效，Agent 结束前要重新测试并查看 Diff。第三是可观测性：Trace 记录调用 ID、参数、错误、Token 和停止原因，重复检测同时检查动作与仓库状态，避免模型原地循环。
>
> 我还做了 Skill、Subagent 和 SWE-bench 实验。简单任务中，强制子代理没有提高 5/5 的成功率，反而增加 67.3% Token 和 88.2% 延迟，说明委托只适合复杂任务。SWE-bench 使用固定 Base Commit 和官方 Docker Harness，3 个分配实例中 1 个成功，成功实例 15 项目标与回归测试全部通过。下一步会扩大到 20–50 个实例并对空 Patch、预算耗尽和错误修复做分类。

### 2.2 中文 RAG

> 我没有直接用高层 RAG 框架，而是把 PDF 解析、中文字符分块、BGE 向量、FAISS、Cross-Encoder 重排、证据约束生成和 RAGAS 串起来，目的是能独立观察每一层的错误。
>
> 在 30 条 Gold QA 上，Dense Recall@10 是 93.33%，但 Recall@1 只有 20%，说明主要瓶颈是排序而非候选召回。加入 Cross-Encoder 后 Recall@1 提升到 60%，MRR 提升到 0.7389，Recall@10 保持不变，符合重排器只改变候选顺序的预期。HyDE 将 Recall@10 提升到 96.67%，但平均每题增加到 18.86 秒，而且 6 个查询退化，因此不能默认全量开启。
>
> 这个项目让我形成了分层评测思路：先检查召回，再检查排序，最后评估生成的忠实度和相关性。当前不足是样本量小，后续会扩大数据并增加引用准确率、无答案识别和 P95 延迟。

### 2.3 LLM 核心与训练对齐

> 这部分从手写 Attention、BPE、Decoder-only Transformer、RoPE 和 KV Cache 开始，并用数值等价测试验证实现；例如 Attention 最大绝对误差约 `7.15e-7`，KV Cache 前后 logits 误差约 `2.86e-6`。
>
> 然后在 Qwen2.5-0.5B 上手写 LoRA、Assistant-only Loss、SFT 和 DPO。LoRA 只训练 0.109% 参数，在受控 CPU 实验中把峰值内存从约 10.78 GB 降到 3.31 GB。SFT 在 80 道 C-Eval 子集上提升 5 个百分点，DPO 在 64 组偏好样本上的胜率从 50% 到 54.69%，但效果较弱。
>
> 最重要的发现来自工具微调：格式合法率达到 100%，Exact Match 只有 5%，说明模型学会了输出外观，但没有真正掌握工具语义。它促使我在后续 Agent 项目中拆分格式、工具选择、参数和最终答案指标。

## 3. Transformer 与推理基础

### Q1：为什么 Attention 要除以 `sqrt(d_k)`？

点积方差会随维度增大，未经缩放的分数容易把 Softmax 推入饱和区，使梯度很小。除以 `sqrt(d_k)` 可让分数尺度更稳定。

### Q2：Padding Mask 和 Causal Mask 有什么区别？

Padding Mask 阻止模型关注补齐位置；Causal Mask 阻止当前位置看到未来 Token。Decoder-only 训练通常同时需要二者。

### Q3：如何证明 Causal Mask 没有泄漏？

改变某个位置之后的未来 Token，再比较该位置及之前位置的输出；若实现正确，前缀输出不应变化。项目中的泄漏测试结果为 0。

### Q4：RoPE 为什么能表达相对位置？

RoPE 对 Query 和 Key 的二维子空间按位置旋转。两者点积中的旋转可合并为位置差对应的旋转，因此注意力分数自然包含相对位置信息。

### Q5：KV Cache 缓存的是什么？为什么不缓存 Query？

缓存历史层的 Key 和 Value。生成下一 Token 时只需要当前 Token 的 Query 去关注历史 KV；历史 Query 不会被后续位置再次使用。

### Q6：KV Cache 的代价是什么？

减少重复计算，但缓存随层数、序列长度、Head 数和 Head Dimension 增长，占用显存；长上下文下可能成为主要内存瓶颈。

### Q7：为什么比较 logits 比比较生成文本更严格？

采样或 Argmax 可能在 logits 有误差时仍得到同一 Token。逐位置比较 logits 能验证缓存和非缓存路径的计算等价。

### Q8：Top-k、Top-p、Temperature 分别控制什么？

Temperature 调整整体分布尖锐程度；Top-k 只保留概率最高的 k 个 Token；Top-p 保留累计概率达到阈值的最小候选集合。三者共同在确定性和多样性之间取舍。

## 4. LoRA、SFT 与 DPO

### Q9：LoRA 为什么能减少训练成本？

冻结原权重 `W`，只学习低秩更新 `BA`，其中秩 `r` 远小于输入和输出维度。优化器状态和梯度只为 A、B 保存，因此显著减少可训练参数与训练内存。

### Q10：LoRA 参数量如何计算？

对形状为 `d_out × d_in` 的线性层，A、B 参数量为 `r × d_in + d_out × r`，再对所有注入层求和。

### Q11：项目中为什么不能说 LoRA 一定比全参微调效果好？

两组使用相同学习率，但最优超参数通常不同；训练预算也较小。实验只支持“该设置下 LoRA 更省资源且 Eval Loss 更低”，不能推出普遍规律。

### Q12：Assistant-only Loss 是什么？

对 System 和 User Token 的 Label 设为 `-100`，只在 Assistant 回复区域计算交叉熵，避免模型被训练去预测输入指令。

### Q13：SFT 的主要局限是什么？

它最大化示范答案概率，但不直接学习两个回答之间的相对偏好；也可能过拟合格式或训练分布。

### Q14：DPO 的直觉是什么？

DPO 让策略模型相对参考模型更偏好 chosen 回答而非 rejected 回答，不需要单独训练奖励模型，也不需要在线 RL rollout。

### Q15：为什么本项目 DPO 提升较弱？

只有 64 组偏好数据、训练预算有限，chosen/rejected 区分可能不够强，也没有多随机种子。54.69% 胜率和很小的 Margin 只能说明轻微趋势。

### Q16：为什么工具调用格式 100% 但 Exact Match 只有 5%？

输出 JSON 模板是低熵模式，容易模仿；正确工具与参数依赖语义理解和组合泛化。训练数据可能覆盖了格式，却没覆盖足够多的工具边界和负例。

## 5. RAG

### Q17：为什么不用 LangChain？

学习目标是看清分块、Embedding、索引、重排和上下文组织的接口及误差来源。生产环境可以使用框架，但前提是知道每层在做什么、如何替换和评测。

### Q18：Recall@k 和 MRR 的区别？

Recall@k 只关心前 k 个结果是否包含相关文档；MRR 使用第一个相关文档排名的倒数，更关注它是否排得足够靠前。

### Q19：为什么 Dense Recall@10 很高但 Recall@1 很低？

Embedding 已能把相关文档放进候选集合，但相似度不足以做精细排序。此时 Cross-Encoder 重排通常比盲目扩大 k 更有价值。

### Q20：Bi-Encoder 和 Cross-Encoder 的差异？

Bi-Encoder 独立编码查询和文档，可预计算文档向量，适合大规模召回；Cross-Encoder 联合编码查询和文档，交互更充分但计算昂贵，适合小候选集重排。

### Q21：重排为什么不改变 Recall@10？

如果重排输入和输出都是相同的 10 个候选，它只改变顺序，不改变集合成员，因此 Recall@10 不变。

### Q22：HyDE 为什么可能有效？

短查询与文档在表达风格上可能有差距。假想答案更接近文档语言，Embedding 后可能更容易命中相关内容。

### Q23：HyDE 为什么也会变差？

假想答案可能引入错误实体或错误方向，使查询表示产生漂移；还增加一次模型调用的延迟和费用。

### Q24：如何决定是否触发 HyDE？

可根据首轮检索最高分、Top1 与 Top2 Margin、查询长度或类型做条件触发，并用离线数据校准阈值，而不是全量开启。

### Q25：Faithfulness 与 Answer Relevancy 的区别？

Faithfulness 检查答案中的陈述能否由上下文支持；Answer Relevancy 检查答案是否真正回应了问题。忠实但答非所问、相关但凭空编造都可能发生。

### Q26：如何减少 RAG 幻觉？

提高检索质量、保留来源元数据、要求逐条引用、对证据不足允许拒答，并在输出后做引用一致性或 Claim-level 验证。

## 6. ReAct、工具调用与 MCP

### Q27：ReAct 的核心是什么？

让模型在推理与行动之间循环：根据问题选择 Action，读取 Observation 后更新下一步决策，直到给出 Final Answer。核心是闭环状态更新，不是必须输出可见的 Thought 文本。

### Q28：原生 Function Calling 后还需要 ReAct 吗？

仍需要“观察结果后继续决策”的循环思想，但不必依赖 `Thought/Action` 文本协议。Action 由结构化 Tool Call 承载，推理可以是模型内部或简短状态。

### Q29：为什么工具描述不应只追求短？

Schema 只告诉模型字段结构，描述还承担适用条件、边界和选择提示。Task5 中简化工具描述使联合成功率从 83.3% 降至 66.7%。

### Q30：Tool Schema 的 `parameters` 为什么是对象而不是列表？

它遵循 JSON Schema：函数参数整体是一个 `object`，各参数放在 `properties` 中，必填项放在 `required` 数组。它完全支持多个命名参数。

### Q31：工具异常后应该直接重试吗？

不应无差别重试。超时和瞬时模型错误可以有限重试；参数错误应让模型修正；未命中应调整查询；权限或安全拒绝通常不可重试。

### Q32：什么算 Agent 的 retried？

应按评测定义区分。对同一意图在收到错误 Observation 后再次尝试，可算恢复重试；主动切换到另一个合理工具更适合记为 fallback。二者都可能成功，但分析意义不同。

### Q33：为什么需要最大步骤数？

防止无限循环和成本失控。达到上限应返回明确停止原因，并保留 Trace，而不是伪造最终答案。

### Q34：MCP 解决什么问题？

MCP 将工具发现、Schema 和调用协议标准化，使 Agent 与文件、数据库、浏览器等能力解耦。它不自动解决工具安全、权限、上下文预算和任务规划。

### Q35：为什么 MCP 客户端常用异步接口？

工具调用可能涉及进程、网络或文件 I/O，异步接口允许等待期间调度其他任务。但如果代码逐个 `await` 且没有并发工作，收益主要是接口兼容和不阻塞事件循环，不会自动加速单条串行链路。

### Q36：为什么必须保留 Tool Call ID？

模型一次可能发出多个调用。结果消息需要用 ID 与原调用配对，否则模型无法可靠知道哪个结果对应哪个请求。

## 7. Coding Agent 工程设计

### Q37：`resolve_path` 的目的是什么？

把模型给出的相对路径规范化为工作区内的真实路径，并验证它没有通过绝对路径、`..` 或符号链接逃离根目录。

### Q38：为什么要保护测试文件？

否则 Agent 可以删除或弱化测试来制造绿色结果。基准要求修复产品代码并通过既定测试，测试本身应视为只读验收合同。

### Q39：为什么写代码后旧测试结果要失效？

测试结论对应某个仓库状态。一旦 Patch 改变，旧结果不再证明当前代码正确；不失效会出现“先测试、后修改、直接宣称通过”的状态漏洞。

### Q40：重复行为如何监测？

不能只看连续两次工具名。工程版可以为标准化工具参数、当前 Patch 哈希、测试状态和错误类型生成状态指纹；动作重复且状态没有进展时才增加重复计数。

### Q41：为什么 Patch 能反映仓库状态？

`git diff` 给出相对 Base 的工作区变化。每次关键动作后取 Patch 摘要，就能判断模型是否真正产生新修改，不必等最终总结才第一次检查。

### Q42：模型返回空内容怎么办？

先判断是否包含合法 Tool Call；若内容和调用都为空，记录 `empty_response`，按上游瞬时故障做有限次数重试。超过上限终止，并保留错误，而不是返回成功。

### Q43：没有 Final Answer 一定代表失败吗？

对需要自然语言交付的任务通常是协议失败，但代码是否修复应由 Patch 和测试独立判断。评测中应分别记录“代码验收成功”和“Agent 协议完成”。

### Q44：Skill 在模型端是不是注册工具？

通常不是。Skill 更像按需注入的说明书、流程和约束；工具是可调用的执行接口。Skill 可以教模型何时、如何组合多个工具。

### Q45：为什么 Skill 用标签封装？

标签提供清晰边界和来源标识，帮助模型区分系统规则、Skill 内容和用户输入，也方便多个 Skill 拼接与 Trace；标签本身不是能力来源。

### Q46：多个 Skill 同时匹配怎么办？

先按任务相关度和具体性排序，再考虑优先级与 Token 预算；去除重复或冲突内容，只加载完成任务所需的最小集合。冲突时系统和项目级规则优先。

### Q47：Subagent 与普通函数调用的区别？

Subagent 有独立模型上下文和多步工作能力，可返回压缩结论；普通工具通常执行确定性动作。Subagent 适合边界清晰、上下文较重的子任务，但成本更高。

### Q48：为什么不让主 Agent 直接继承所有子代理逻辑？

可以复用模型客户端、工具循环等基础设施，但委托策略、上下文构造和结果汇总属于不同职责。用组合或薄继承可避免把主 Agent 与特定子任务强耦合。

## 8. 实验设计与指标追问

### Q49：联合成功是什么意思？

所有必要条件同时满足。例如答案正确、必需工具覆盖、没有多余工具且错误已恢复。它比单看最终答案更严格，可防止模型猜对答案却没有按要求使用工具。

### Q50：故障恢复率为什么有两个分母？

总体恢复率以所有计划运行作分母，反映完整实验表现；条件恢复率只以故障确实注入成功的运行作分母，回答“遇到故障后能否恢复”。二者不能混用。

### Q51：如何验证 `max_size` 或 `timeout` 真生效？

构造低于、等于和高于边界的黑盒样本；检查时间、退出类型、截断标志和保留内容，而不只是断言配置字段等于某个值。

### Q52：为什么无异常、空 stdout、未命中、截断要分别处理？

它们对应不同状态：执行成功但沉默、合法无结果、结果过长。若统一当异常，模型会错误重试，指标也无法区分数据问题、搜索策略与资源限制。

### Q53：为什么实验要重复三轮？

模型采样和远程服务存在随机性，单轮可能偶然成功。重复运行可报告均值和失败分布；更严谨时还应增加样本量、随机种子和置信区间。

### Q54：为什么不能根据延迟直接判断 14B 比 8B 快？

远程 API 的排队、批处理、硬件和负载未知，端到端延迟混入服务端因素。结果只能描述本次服务条件，不能当成模型规模的纯因果效应。

### Q55：为什么 Skill 实验成功率不变仍有价值？

它说明简单任务存在天花板，额外上下文有成本；也暴露当前数据无法检验 Skill 的真正价值。负结果帮助调整任务难度和触发策略。

### Q56：如何让实验更公平？

固定数据、模型、温度、最大步骤和工具集合，每次只改变一个目标变量；保存原始 Trace；预先定义指标；对失败做分类，并报告样本量和置信区间。

## 9. 压力面试题

### Q57：这些不都是教程项目吗？

> 项目确实源于系统学习路线，我不会把它包装成生产业务。但我没有停留在照着接口跑通：关键模块是手写的，Agent 项目补了安全边界、状态一致性和 Trace；每个阶段都有对照实验与失败分析，SWE-bench 还使用官方 Docker 验收。它能证明我的基础和工程方法，生产规模与线上治理则是下一步需要在岗位中继续积累的部分。

### Q58：SWE-bench 才 1/3，为什么写进简历？

> 因为我把它作为诚实的系统验收，而不是只挑成功 Demo。成功实例证明从定位、修改到官方测试的链路可行；两个空 Patch 暴露了规划和工具预算问题。这个结果比未经官方测试的“看起来修好了”更有信息量，下一步重点也是扩大样本并分析失败类型。

### Q59：Qwen-Agent 为什么比你的手写 Agent 强？

> 它在本轮任务上联合成功率更高，可能来自更成熟的工具协议、默认提示、解析与循环控制。但实验同时改变了框架、Prompt 和调用协议，不能把差异只归因于某个“自带 Prompt”。要确认原因，需要同模型、同工具描述、同最大步骤做逐项消融。

### Q60：既然原生 Function Calling 更稳，为什么还要手写 ReAct？

> 手写 ReAct 的价值是理解 Agent 状态机、Observation 回填、错误恢复和停止条件。掌握这些后再使用原生 Function Calling，才能知道结构化调用解决了文本解析问题，但没有替代运行时、安全和评测。

### Q61：项目里最有价值的失败是什么？

> 一是工具微调格式合法率 100% 但 Exact Match 只有 5%，让我开始拆分格式与语义指标；二是 SWE-bench 聚合最初只统计非空候选，容易显示 1/1，我把官方结果回填到全部分配实例，最终如实报告 1/3。它们都说明评测代码本身也必须被审查。

### Q62：如果让你把 Coding Agent 做到生产可用，还缺什么？

> 至少缺少更强的容器级隔离和权限系统、长上下文压缩、持久化任务状态、并发与队列、成本预算、可回放 Trace、人工审批点、更多语言和仓库测试，以及更大规模基准和线上反馈闭环。

## 10. 行为题素材

### 最困难的问题

SWE-bench 的 Base Commit 在部分克隆中不存在。处理方式：先从错误日志定位为 Git 对象缺失，而非 Agent 代码错误；增加完整性和 Commit 预检；为每个实例使用隔离检出；最后用官方 Harness 复验。

### 一次主动纠错

聚合报告把 1 个非空候选显示成 1/1，没有体现另外 2 个空 Patch。发现分母语义错误后，按实例 ID 合并官方结果，增加未提交状态与全集 Resolve Rate，并添加自动测试。

### 一次负实验

强制 Subagent 在 5 个简单任务上成功率没有变化，却增加 67.3% Token 和 88.2% 延迟。结论不是“子代理没用”，而是需要任务复杂度分类和条件委托。

### 一次取舍

RAG 中 HyDE 提高总体召回，但增加明显延迟且使 6/30 个查询退化。因此更合理的方案是条件触发，而不是为了平均分全量开启。
