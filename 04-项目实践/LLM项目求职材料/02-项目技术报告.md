# LLM 项目技术报告

> [!summary]
> 这套项目从 Transformer 基础结构出发，依次覆盖预训练模型结构、参数高效微调与偏好对齐、RAG、工具调用 Agent、MCP Coding Agent。真正有价值的部分不是功能数量，而是形成了“**实现机制—设置对照—采集 Trace—离线验收—分析边界**”的闭环。

## 1. 项目全景

| 阶段 | 原始任务 | 核心问题 | 主要产物 |
|---|---|---|---|
| 模型基础 | Task1 | 注意力和掩码如何工作 | Transformer 编码器与情感分类器 |
| 生成模型 | Task2 | Decoder-only、RoPE、KV Cache 如何工作 | Mini GPT 与生成采样 |
| 训练对齐 | Task3 | 如何低成本微调并进行偏好优化 | LoRA、SFT、DPO、工具格式微调 |
| 知识增强 | Task4 | 如何检索、重排并约束答案 | 中文 RAG 与 RAGAS 评测 |
| 工具 Agent | Task5 | 模型如何在思考、调用工具和回答间循环 | ReAct Agent 与多维消融实验 |
| Coding Agent | Task6 | 如何让 Agent 安全地修改和验证代码 | MCP、Skills、Subagent、SWE-bench |

用于简历时，应将其归并为：

1. LLM 核心与训练对齐
2. 中文 RAG 检索评测
3. 工具调用与 Coding Agent

## 2. 项目一：LLM 核心机制与训练对齐

### 2.1 目标

不是调用现成模型完成分类，而是理解从张量计算到训练目标的关键环节：

- Attention 的缩放、掩码和多头拼接；
- BPE 的训练、编码与解码；
- Decoder-only 因果建模；
- RoPE 的相对位置信息；
- KV Cache 的增量推理；
- LoRA、SFT、DPO 的参数与损失设计。

### 2.2 架构与验证

```text
文本
  └─ Tokenizer / BPE
      └─ Embedding + Position / RoPE
          └─ Attention + MLP
              ├─ 分类头：情感分类
              └─ LM Head：自回归生成
                    └─ LoRA → SFT → DPO
```

关键数值验证：

| 验证项 | 结果 | 意义 |
|---|---:|---|
| 手写 Attention 与参考实现最大绝对误差 | `7.15e-7` | 基本排除矩阵排列和缩放错误 |
| 因果掩码未来信息泄漏 | `0` | 未来 Token 未参与当前预测 |
| KV Cache 前后 logits 最大误差 | `2.86e-6` | 增量推理与全量推理数值一致 |
| 情感分类 Dev Accuracy | 84.5% | 基础编码器能够完成受控任务 |
| 小型诗歌语料 Dev PPL | 45.16 | 达到该教学任务设定阈值 |

### 2.3 LoRA、SFT 与 DPO 实验

在 Qwen2.5-0.5B 上完成手写 LoRA 注入、Chat Template、Assistant-only Loss、SFT 与 DPO。

LoRA 对照结果：

| 方案 | 可训练参数 | 峰值内存 | 用时 | Eval Loss |
|---|---:|---:|---:|---:|
| Full Fine-tuning | 494,032,768 | 约 10.78 GB | 130.20 s | 2.3385 |
| LoRA | 540,672 | 约 3.31 GB | 68.95 s | 1.1015 |

结论与边界：

- LoRA 可训练参数占比为 0.109%，本次实验峰值内存降低约 69.3%，用时减少约 47%。
- 两组沿用相同学习率，因此 Loss 差异不能简单归结为 LoRA 天生更好；Full Fine-tuning 可能需要不同超参数。
- 该数据是 CPU 进程峰值内存，不是 GPU 显存。

Rank 消融中，`r=4/8/16/32` 的 Eval Loss 差距小于 0.003，低 Rank 在当前数据量和训练预算下性价比最高。但固定 `alpha=16` 意味着缩放比例 `alpha/r` 同时发生变化，Rank 不是唯一变量。

下游评测：

- 80 道 C-Eval 子集：Base 37.5%，SFT 42.5%，提升 5 个百分点。
- 64 组偏好样本：SFT 胜率 50%，DPO 54.69%，平均 Margin 仅 0.000536。
- 20 条工具调用：格式合法率 100%，Exact Match 5%。

最后一项揭示了重要问题：**格式对不等于语义对**。模型容易学会 JSON 外壳，但工具选择和参数抽取仍需更丰富的数据及独立指标。

### 2.4 可讲的工程思考

- 单元测试不仅测形状，还要测数值等价和信息泄漏。
- 训练实验必须记录参数量、资源占用、时间、损失和下游指标。
- 一个总分会掩盖错误类型，应拆分格式、工具名、参数和最终答案。
- 小样本上的正向结果要报告样本量和随机性，不能写成普适结论。

## 3. 项目二：中文 RAG 检索与评测系统

### 3.1 目标

从零搭建可解释的中文 RAG 链路，避免高层框架隐藏关键决策，并回答三个问题：

1. 候选文档能否被召回？
2. 正确文档能否排到前面？
3. 最终答案是否忠于证据且回答问题？

### 3.2 数据流

```text
PDF
  → 文本提取
  → 字符分块 + 页码/来源元数据
  → BGE Embedding
  → FAISS Dense Retrieval
  → Cross-Encoder Rerank
  → Top-k Context
  → 证据约束生成
  → RAGAS / 人工错误分析
```

选择字符分块是为了降低中文分词依赖并快速建立基线，但它会切断句义和章节结构，因此属于教学基线而非最终方案。

### 3.3 检索与重排实验

30 条 Gold QA 的结果：

| 方案 | Recall@1 | Recall@10 | MRR |
|---|---:|---:|---:|
| Dense Retrieval | 0.2000 | 0.9333 | 0.4567 |
| Dense + Rerank | 0.6000 | 0.9333 | 0.7389 |

Cross-Encoder 没有扩大候选集合，因此 Recall@10 保持不变；它的价值是把已召回的相关文档移到更前面。Recall@1 从 20% 提升到 60%，比只看 Recall@10 更能证明排序改善。

### 3.4 HyDE 与生成评测

HyDE 先让模型生成一个“假想答案”，再用其表示进行检索：

- Recall@10：96.67%
- MRR：0.5886
- 平均延迟：18.86 秒/题
- 6/30 个查询的排名反而变差

因此 HyDE 不能无条件开启。更合理的生产策略是根据查询类型、首轮检索置信度或预算决定是否触发。

5 条端到端样本上的 RAGAS：

- Faithfulness：0.8333
- Answer Relevancy：0.8744

这能检查答案是否基于上下文及是否回答问题，但样本过少，且评测模型本身也可能有偏差，应配合引用命中率和人工错误分类。

### 3.5 可讲的工程思考

- 召回与排序是不同问题，需要 Recall@k 和 MRR/NDCG 分别衡量。
- 重排只对候选集合内部排序，召回阶段漏掉的文档无法被它挽回。
- RAG 的端到端正确率由检索、上下文组织和生成共同决定。
- 评测集应按事实型、多跳、时间敏感、无答案等查询类型分层。

## 4. 项目三：工具调用与 Coding Agent

### 4.1 从 ReAct 到原生 Function Calling

Task5 的手写 ReAct 循环为：

```text
Question
  → Thought
  → Action + Action Input
  → Tool Router
  → Observation
  → 下一轮 Thought
  → Final Answer
```

真正的关键不是字符串模板，而是运行时状态机：

- 解析模型输出；
- 校验工具名和参数；
- 将工具异常转成模型可理解的 Observation；
- 控制最大步骤、超时与重试；
- 记录每一步 Trace；
- 判定最终答案，而不是把任意文本都当成功。

现代原生 Function Calling 将 Action 变成结构化 `tool_calls`，可减少脆弱的文本解析，但循环控制、工具执行、安全隔离和评测仍由 Agent 运行时负责。

### 4.2 Task5 对照实验

每个条件 10 个任务、重复 3 轮，共 30 次运行。

| 实验 | 核心结果 | 应得结论 |
|---|---|---|
| 框架对比 | Qwen-Agent 联合成功率 100%；手写 ReAct 90% | 成熟框架默认协议更稳，但框架、Prompt、循环同时变化，不能只归因于“自带 Prompt” |
| 模型规模 | 0.6B/8B/14B 联合成功率 36.7%/63.3%/76.7% | 规模增大总体改善工具使用；远程服务负载使延迟不严格单调 |
| Prompt 消融 | Baseline 83.3%；去 Few-shot 83.3%；简化工具描述 66.7% | 当前任务中 Few-shot 无明显收益，工具语义说明比表面简洁更重要 |
| 故障恢复 | 总体 66.67%；成功注入条件下 90.91% | 必须区分“故障是否真的注入”与“注入后是否恢复” |

手写 ReAct 的 30 次运行还取得：答案正确率 96.7%、工具覆盖率 90%、工具精确匹配率 90%、联合成功率 90%、平均 1.2 次工具调用。

### 4.3 Coding Agent 架构

Task6 将工具 Agent 扩展到代码仓库：

```text
用户任务
  → CodeAgent
      ├─ Model Client
      ├─ Native Tool Loop
      ├─ Skill Loader（渐进披露）
      ├─ Delegate Agent（独立上下文）
      └─ Trace / Usage / Stop Policy
            ↓ MCP stdio
      Repository Tools
      ├─ list/search/read
      ├─ write/apply patch
      ├─ run tests
      └─ git diff
            ↓
      受保护工作区
```

### 4.4 安全与一致性设计

代码 Agent 的风险不只来自 shell，还来自文件系统和状态错配：

- `resolve_path` 将用户路径解析到工作区根目录下，并检查 `..`、绝对路径与符号链接逃逸。
- 禁止访问 `.git`，避免模型篡改仓库元数据。
- 仅允许修改受控源码，并保护测试文件，避免通过改测试“制造通过”。
- 子进程固定 `cwd`，配置超时和 stdout/stderr 截断，防止卡死或上下文爆炸。
- 写文件或应用 Patch 后，将旧测试结果标记失效，要求重新验证。
- Trace 记录调用 ID、参数、结果、错误、Token Usage 和停止原因。
- 重复行为检测不仅比较工具名，也比较标准化参数、仓库 Patch 和测试状态，从而识别“看似在工作但没有进展”。

### 4.5 Skill 与 Subagent 实验

Skill 不是简单注册一个工具。它是可匹配、按需加载的过程知识，通常通过系统上下文或消息注入告诉模型“如何完成一类任务”；工具则提供“能执行什么动作”。

Subagent 拥有独立上下文，适合把测试分析、资料查找等工作隔离出去，避免主上下文被大量细节污染。但委托存在固定成本。

5 个简单任务的结果：

| 条件 | 成功率 | 平均耗时 | 平均 Token | 解释 |
|---|---:|---:|---:|---|
| Baseline | 5/5 | 9.906 s | 11,281.2 | 基线 |
| 强制 Subagent | 5/5 | 18.645 s | 18,874.0 | 成功率不变，Token +67.3%，延迟 +88.2% |
| 条件委托 | 5/5 | 7.021 s | 10,152.4 | 本轮没有触发委托，不能把改善归因于 Subagent |
| Baseline（Skill 实验） | 5/5 | 6.791 s | 9,540 | 基线 |
| 开启 Skill | 5/5 | 7.058 s | 10,499 | Match Rate 80%，成功率不变，Token 约 +10% |

结论：Skill 和 Subagent 是复杂任务的结构化能力，不是免费增益。简单任务中额外上下文和调用轮次可能只增加成本。

### 4.6 SWE-bench 官方验收

S4 使用固定 Base Commit、隔离检出和官方 Docker Harness，避免在错误版本或污染工作区上得出结论。

本轮分配 3 个 Astropy SWE-bench Lite 实例：

- `astropy__astropy-12907`：生成 506 字节 Patch，官方评测 resolved；2 项 FAIL_TO_PASS 与 13 项 PASS_TO_PASS 全部通过。
- 其余 2 个实例：在最大工具预算内没有生成非空 Patch，记为失败。
- 总体 Resolve Rate：1/3，即 33.33%。

这里必须区分：

- **已提交候选通过率**：1/1；
- **分配任务总体通过率**：1/3。

简历和报告应采用后者，前者只用于解释该 Patch 的有效性。

### 4.7 关键失败案例

#### 案例一：部分克隆无法检出 SWE-bench Base Commit

症状：本地仓库有目标项目，但缺少基准指定的历史对象，隔离工作区创建失败。

修复：在正式运行前增加仓库完整性和 Base Commit 预检，必要时获取完整历史；每个实例使用独立检出，禁止复用污染状态。

领悟：Git 仓库“存在”不等于基准所需对象“完整”，基准验收首先要保证输入状态可复现。

#### 案例二：报告只统计非空候选

症状：官方结果显示 1/1 resolved，容易误读成三个分配任务全部成功。

修复：将官方结果按实例 ID 回填到候选生成报告，未提交实例明确标记 `not_submitted_empty_patch`，总分母固定为分配实例数。

领悟：聚合逻辑属于评测正确性的一部分，错误分母会让技术结果失真。

## 5. 统一评测方法

### 5.1 先定义成功事件

工具 Agent 的“成功”可以至少拆成：

- 最终答案正确；
- 必需工具全部被调用；
- 没有多余或错误工具；
- 工具参数正确；
- 工具执行成功；
- 整个任务在预算内完成。

联合成功应定义为多个必要条件同时成立，而不是任意单项通过。例如：

```text
joint_success = answer_correct
                AND required_tools_covered
                AND exact_tool_sequence
                AND no_unrecovered_error
```

### 5.2 为什么异常类型要分开

| 现象 | 真实语义 | 处理方式 |
|---|---|---|
| 工具抛异常 | 执行失败 | 返回结构化错误，允许修正或重试 |
| 空 stdout | 命令成功但没有标准输出 | 不能自动判失败，应结合退出码和预期 |
| 搜索未命中 | 合法查询没有结果 | 提示扩大范围或换关键词 |
| 输出被截断 | 已产生结果但上下文装不下 | 标记 truncated，引导缩小查询 |
| 模型空响应 | 上游未给出可执行内容 | 有限重试，超过次数终止 |

如果把它们统一成“工具失败”，模型无法选择正确恢复策略，评测也无法定位瓶颈。

### 5.3 配置如何证明生效

以 `max_size` 或 `timeout` 为例，不能只检查配置值被读取，而要构造跨越边界的黑盒测试：

- `max_size`：准备小于、等于、大于阈值的输出，验证边界行为及 `truncated` 标志。
- `timeout`：运行一个明显超过阈值的可控命令，验证在允许误差内终止，并返回超时类型而非普通异常。
- 同时测试非法值，如负数、零和错误类型，确保配置失败得足够早。

## 6. 项目局限与补强路线

| 项目 | 当前局限 | 优先补强 |
|---|---|---|
| Task1–2 | 数据规模小，缺少吞吐基准 | 增加更大语料、KV Cache 延迟与显存曲线 |
| Task3 | 单随机种子，训练预算小，部分变量耦合 | 多种子、独立学习率搜索、置信区间 |
| Task4 | Gold QA 仅 30 条，RAGAS 仅 5 条 | 扩至 100+ 条并按查询类型切片，增加引用准确率和 P95 延迟 |
| Task5 | 文本 ReAct 与成熟框架不完全同协议 | 增加同模型同 Prompt 的原生 Function Calling 对照 |
| Task6 | S1 量化实验未完成，SWE-bench 仅 3 题 | 完成量化消融，扩至 20–50 个固定实例并报告成本分布 |

推荐补强顺序：

1. Task6 扩大 SWE-bench 样本并做失败分类；
2. Task4 扩大问答集并加入端到端引用校验；
3. Task6 完成 S1 量化实验；
4. Task5 增加公平的 Function Calling 对照；
5. Task3 做多随机种子和超参数控制。

## 8. 自测

1. 为什么 KV Cache 的测试要比较 logits，而不只是比较生成文本？
2. 为什么 Rank 消融中固定 `alpha` 仍然存在混杂变量？
3. Reranker 为什么能提高 Recall@1，却不能找回 Dense 阶段完全漏掉的文档？
4. 为什么工具调用格式合法率 100% 仍可能是一个很差的模型？
5. Skill 和工具的本质差异是什么？
6. 为什么强制 Subagent 在简单任务上可能更差？
7. SWE-bench 中为什么必须使用固定 Base Commit 和官方测试？
8. 为什么 1/1 resolved 不能作为本轮 S4 的总成绩？

<details>
<summary>参考答案</summary>

1. 不同 logits 可能碰巧采样出相同文本，比较每个位置的 logits 能更严格地验证缓存前后计算等价。
2. LoRA 更新通常带有 `alpha/r` 缩放；改变 `r` 而固定 `alpha` 会同时改变缩放比例，因此观察到的变化不只来自秩。
3. Reranker 只接收首阶段候选，能够重排却不能访问候选集合之外的文档。
4. 格式合法只说明 JSON 或调用协议正确，工具名、参数、调用时机和最终答案都可能错误。
5. 工具是可执行能力及其 Schema；Skill 是完成一类任务的过程知识和策略，通常按匹配结果注入上下文。
6. 委托需要额外模型调用、上下文传递和结果汇总；任务过简单时，这些固定成本超过上下文隔离收益。
7. Base Commit 确保 Patch 应用于统一起点，官方测试同时检查缺陷修复与回归；否则结果不可复现也不可比较。
8. 1/1 只统计非空提交，忽略两个没有生成 Patch 的分配实例。总体成绩必须以全部 3 个分配实例为分母，即 1/3。

</details>
