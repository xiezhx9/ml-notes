# LLM 项目简历表述

> [!summary]
> 六个 Task 不建议在简历上拆成六个课程作业。更合适的做法是合并为三个有完整技术主线的项目：**LLM 核心与对齐实验、中文 RAG 检索评测系统、工具调用与 Coding Agent 评测平台**。其中 Coding Agent 最适合作为主项目。

## 1. 求职定位

最匹配的岗位顺序：

1. LLM 应用 / Agent 工程师
2. AI 应用工程师 / RAG 工程师
3. 大模型算法工程师（偏训练、对齐与评测）

建议简历顶部技能栏：

- **语言与框架**：Python、PyTorch、pytest、uv、Git、Docker
- **模型原理**：Transformer、BPE、RoPE、KV Cache、LoRA、SFT、DPO
- **检索与 Agent**：BGE、FAISS、Cross-Encoder、RAGAS、ReAct、Function Calling、MCP、Skills、Subagent、SWE-bench
- **工程与评测**：结构化 Trace、超时与输出截断、路径沙箱、错误恢复、消融实验、离线评测

## 2. 一页简历推荐版本

### 项目一：工具调用与 Coding Agent 评测平台

**技术栈：Python / OpenAI-compatible API / MCP / pytest / Git / Docker / SWE-bench**

- 从零实现文本 ReAct 与原生 Function Calling 两类 Agent 循环，支持工具路由、参数校验、异常反馈、模型重试、重复行为检测和结构化 Trace；进一步基于 MCP stdio 构建具备文件检索、代码修改、测试执行和 Git Diff 检查能力的 Coding Agent。
- 为代码执行链路加入工作区路径解析、符号链接越界防护、`.git` 与测试文件保护、命令超时和输出上限；建立 85 项离线测试，覆盖工具协议、安全边界、Skill 加载、子代理委托与实验聚合。
- 设计框架、模型规模、提示词、故障恢复、Skill 和 Subagent 等对照实验：Task5 手写 ReAct 在 30 次运行中联合成功率为 90%，故障注入后的条件恢复率为 90.91%；Task6 在官方 Docker SWE-bench 验证中完成 1/3 个分配实例，其中成功实例的 2 项 FAIL_TO_PASS 与 13 项 PASS_TO_PASS 测试全部通过。

可附项目链接：

- [ReAct Tool Agent](https://github.com/xiezhx9/react-tool-agent-from-scratch)
- [Coding Agent](https://github.com/xiezhx9/coding-agent-from-scratch)

### 项目二：中文 RAG 检索与评测系统

**技术栈：Python / BGE / FAISS / Cross-Encoder / RAGAS**

- 不依赖 LangChain、LlamaIndex 等高层框架，搭建 PDF 解析、分块与元数据、向量化、FAISS 检索、Cross-Encoder 重排、证据约束生成和 RAGAS 评测的完整中文 RAG 链路。
- 在 30 条人工标注问答上，Dense Retrieval 的 Recall@10 达到 93.33%；加入重排后 Recall@1 从 20% 提升至 60%，MRR 提升至 0.7389，同时保持 Recall@10 不变。
- 实现 HyDE 查询扩展并分析收益边界：Recall@10 提升至 96.67%、MRR 提升至 0.5886，但有 6/30 个查询排名退化；在 5 条端到端样本上获得 Faithfulness 0.8333、Answer Relevancy 0.8744，并据此识别小样本评测与生成延迟问题。

项目链接：[RAG from Scratch](https://github.com/xiezhx9/rag-from-scratch)

### 项目三：LLM 核心机制、参数高效微调与偏好对齐实验

**技术栈：Python / PyTorch / Transformers / PEFT 思想 / Qwen2.5**

- 手写实现多头注意力、因果掩码、BPE、Decoder-only Transformer、RoPE 与 KV Cache；数值校验中注意力实现最大绝对误差为 `7.15e-7`，KV Cache 前后 logits 最大误差为 `2.86e-6`。
- 基于 Qwen2.5-0.5B 手写 LoRA 注入、Assistant-only Loss、SFT 与 DPO 训练链路；LoRA 仅训练 540,672 个参数，占模型参数 0.109%，在受控 CPU 实验中将峰值内存从约 10.78 GB 降至 3.31 GB。
- 建立 Rank 消融、C-Eval、偏好胜率和工具调用评测：SFT 在 80 道 C-Eval 子集上由 37.5% 提升至 42.5%；DPO 在 64 组偏好样本上的胜率由 50% 提升至 54.69%，并发现工具调用微调更容易学会输出格式而非正确的工具语义。

- [Mini GPT](https://github.com/xiezhx9/mini-gpt-from-scratch)

## 5. 为什么这些项目不只是“简单作业”

项目复杂度不应靠堆功能描述，而应体现四类能力：

| 能力 | 项目证据 |
|---|---|
| 原理理解 | 手写注意力、BPE、RoPE、KV Cache、LoRA、ReAct 循环 |
| 工程约束 | 路径沙箱、超时、输出截断、测试保护、Trace、Git 状态检查 |
| 实验设计 | 框架/模型/提示词/Rank/Skill/Subagent 等对照与消融 |
| 诚实评测 | 区分格式正确与任务正确、条件恢复率与总体恢复率、官方通过率与提交通过率 |

面试时不要说“我实现了一个类似 Codex 的系统”，而要说：

> 我实现了一个教学规模但评测闭环完整的 Coding Agent 原型，重点验证工具协议、安全执行、上下文注入和官方 SWE-bench 验收，而不是宣称达到生产级 Codex 的能力。

## 6. 不建议写进简历的表述

- “SWE-bench 通过率 100%”：实际是已提交的 1 个候选通过，分配全集为 1/3。
- “LoRA 将显存降低 69%”：该实验采集的是 CPU 峰值内存，应写“峰值内存”。
- “DPO 显著提升偏好对齐”：64 个样本上的提升较弱，没有置信区间与多随机种子。
- “RAG 达到生产级准确率”：评测集只有 30 条，RAGAS 端到端样本只有 5 条。
- “Skill/子代理显著提升成功率”：简单任务上成功率均未提升，强制子代理还增加了 67.3% Token 与 88.2% 延迟。
- “六个独立大型项目”：这些是同一学习路线上的递进项目，合并表达更可信。

## 9. 自测

1. 为什么将六个 Task 合并成三个项目更适合简历？
2. Task6 的 SWE-bench 成绩应该如何准确描述？
3. 为什么不能把 LoRA 实验中的内存指标直接写成显存？
4. 面试官认为项目只是教程复现时，应如何回应？

<details>
<summary>参考答案</summary>

1. 因为招聘方关注问题规模、技术主线和闭环能力。合并后分别体现模型训练、RAG、Agent 三条完整链路，也避免六个小项目显得零散。
2. 分配了 3 个实例，生成 1 个非空候选并通过官方 Docker 评测，因此总体是 1/3；该候选自身为 1/1 resolved，但不能用后者替代总体分母。
3. 实验运行在 CPU 并采集进程峰值内存，没有采集 GPU 显存，替换概念会构成夸大。
4. 承认项目源于学习路线，然后强调自己手写了关键机制、设计了对照实验、记录了失败与边界，并能拿出测试、Trace 和官方评测证据。不要伪装成生产项目。
