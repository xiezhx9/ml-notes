# Prompt Cache 与 Codex Agent 上下文

> [!summary] 核心结论
> Prompt cache 复用的是相同 Prompt 前缀对应的模型计算状态，而不是直接复用答案。Codex 这类 Agent 天然包含系统指令、工具定义、项目规则和持续增长的会话历史，因此很适合从 Prompt cache 获益；但缓存只提升成本和延迟效率，不会让模型本身变得更聪明。

## 1. Prompt cache 缓存什么

Transformer 处理输入 token 时，会在每层计算 Key/Value 等中间状态。若后续请求拥有相同的开头，模型可以复用这段前缀已经计算好的 KV 状态，只处理新追加的内容。

```text
请求 1：AAAA
请求 2：AAAABB    -> 复用 AAAA，只计算 BB
请求 3：AAAABBCC  -> 复用 AAAABB，只计算 CC
```

这里要求的是**从开头开始的精确前缀匹配**，不是语义相似，也不要求整个请求完全相同。输出仍然会重新生成，因此相同 Prompt 不保证产生完全相同的答案。

Prompt cache 与生成阶段的普通 KV cache 密切相关，但使用范围不同：

| 机制 | 复用范围 | 主要收益 |
|---|---|---|
| 生成阶段 KV cache | 同一次生成中已处理的历史 token | 避免每生成一个 token 都重算全部历史 |
| Prompt cache | 多次模型请求之间的相同 Prompt 前缀 | 降低重复输入的计算成本和首 token 延迟 |

生成阶段 KV cache 的原理见 [[Task2-03-Causal-Attention与KV-Cache]]。

## 2. 为什么多轮对话反而容易命中

多轮请求虽然每次都携带上下文，但通常采用追加式结构：

```text
第一轮：系统指令 + 工具定义 + U1
第二轮：系统指令 + 工具定义 + U1 + A1 + U2
第三轮：系统指令 + 工具定义 + U1 + A1 + U2 + A2 + U3
```

第二轮可以复用第一轮开头，第三轮又可以复用更长的历史。只要旧消息没有被改写，新增的用户消息不会破坏它之前的缓存前缀。

因此，影响缓存命中的关键不是“每个用户的完整上下文是否相同”，而是：

1. 第一个变化发生在什么位置。
2. 变化之前是否存在足够长且符合条件的缓存断点。
3. 缓存是否仍有效，请求是否被正确路由。

如果把时间戳、用户 ID 或随机数放在 Prompt 最前面，差异会过早出现，使后面即使有大量相同内容也难以复用。稳定内容应放在前面，动态内容应尽量靠后。

## 3. 不同用户之间怎样复用

同一个 Agent 应用通常具有共同的基础前缀：

```text
平台基础指令
+ 开发者指令
+ 工具定义与 Schema
+ 固定示例或参考资料
+ 用户专属上下文
+ 当前问题
```

即使用户对话不同，前面的应用规则和工具定义仍可能完全一致。服务端可以复用公共前缀，也可以通过 cache key 将不同客户、用户或工作流分开核算和路由。

以 OpenAI 的公开实现为例，缓存不会跨组织或区域处理边界共享。`prompt_cache_key` 可以影响路由或隔离缓存核算，但它不是缓存条目的直接地址，也不能保证命中。

## 4. Codex 提交给模型的上下文

OpenAI 没有公开 Codex 最终渲染 Prompt 的完整原文。按照公开文档，可以近似理解为以下结构：

| 层级 | 典型内容 | 稳定性 |
|---|---|---|
| 平台系统指令 | 模型身份、基础行为、安全边界、指令优先级 | 高 |
| 工具定义 | 工具名称、说明、参数 Schema、调用约束 | 较高，启停工具时变化 |
| Codex 产品指令 | 代码修改、测试、Git、权限、汇报等工作规则 | 高 |
| 用户与项目指令 | 全局及项目 `AGENTS.md`、目录级覆盖规则 | 项目内较高 |
| Skills 信息 | 初始 Skill 名称、简介、路径；激活后加载完整 `SKILL.md` | 按任务变化 |
| 运行环境 | 工作目录、Shell、日期、沙箱、网络和可写路径 | 部分动态 |
| 会话与工具轨迹 | 历史消息、工具调用、工具结果、子代理结果 | 追加增长 |
| 当前输入 | 最新用户消息、附件和临时上下文 | 动态 |

这不是八段固定文本，而是便于理解的逻辑划分。实际请求是包含角色、文本、工具和多模态内容的结构化上下文。

### AGENTS.md

Codex 启动时会构建指令链：先读取全局规则，再从项目根目录沿路径读取到当前工作目录。越靠近当前目录的文件越晚进入合并 Prompt，因此可以覆盖较早的通用规则。

### Skills

Skills 使用渐进式加载。初始上下文通常只包含名称、简介和路径；当任务匹配某个 Skill 后，Codex 才读取完整 `SKILL.md`。这可以避免把所有已安装 Skill 的完整内容都塞进每一轮上下文。

### 文件和工具结果

Codex 通常不会自动把整个仓库发送给模型。它先通过搜索、目录和文件读取工具按需取得内容，随后工具调用及其结果进入会话轨迹，成为后续推理的上下文。

权限也不只靠 Prompt 约束。模型会收到相关规则，但真正的文件、网络和命令边界还由 Codex 外层的沙箱与审批机制强制执行。

## 5. 哪些变化会破坏缓存

常见原因包括：

- 更换模型或相关推理配置。
- 改变工具名称、描述、Schema 或排列顺序。
- 修改系统、开发者或 `AGENTS.md` 指令。
- 在前缀中加入时间戳、随机值等动态内容。
- 重写、截断或重新总结历史消息。
- Compaction 用压缩结果替换旧上下文。
- 缓存过期、容量淘汰或请求被路由到其他节点。
- 相同前缀没有达到模型要求的最低可缓存长度。

OpenAI 文档显示，GPT-5.6 及后续模型的最低可缓存前缀为 1,024 个可见输入 token。隐藏系统内容不计入这个最低长度。具体门槛、缓存读写价格和保留时间可能随模型变化，应以当前模型文档为准。

## 6. Prompt cache 是否代表 Agent 更先进

需要区分基础设施和 Agent 架构：

- **Prompt cache 本身不是智能。** 它只是复用已完成的计算，不改变模型的推理能力和输出生成方式。
- **缓存友好的上下文设计体现工程成熟度。** 稳定指令顺序、保持工具 Schema 稳定、追加历史、按需加载工具与 Skills，并谨慎选择 Compaction 时机，可以显著降低长任务的成本和延迟。

真正决定 Agent 能力的仍是规划、工具选择、状态维护、记忆管理、错误恢复、权限控制和结果验证。Prompt cache 的作用，是让这些机制在长上下文和多轮工具调用中运行得更高效。

## 7. 与 Compaction、工作记忆的区别

| 机制 | 解决的问题 | 是否改变模型可见内容 |
|---|---|---|
| Prompt cache | 相同前缀被重复计算 | 否 |
| Compaction | 上下文过长、放不下或成本过高 | 是，用压缩内容替换部分历史 |
| 工作记忆 | Agent 接下来需要记住哪些目标、进度和证据 | 是，需要在后续请求中重新读入 |

Compaction 可能降低首次缓存命中，因为压缩后的前缀与原历史不同；但总输入变短后，整体成本仍可能下降。因此不能只看缓存命中率，应同时比较输入 token、缓存读写成本、延迟和任务成功率。

## 8. API 计费与订阅额度

API 命中 Prompt cache 后，缓存输入通常有单独价格；部分模型还会区分缓存写入和读取。ChatGPT 或 Codex 的订阅额度属于另一层产品规则，不能直接用 API 的缓存折扣比例推算订阅额度消耗。
